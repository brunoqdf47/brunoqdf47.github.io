Case study · enterprise integration

A blocked connector, and the stronger system it forced.

An internal team needed automated intake — a form submission becoming a tracked work item on a GitHub board. The fast low-code path hit a corporate security guardrail. Rerouting the work to where it belonged — inside the network, under orchestration — didn't just unblock it. It produced a more reachable, auditable, and lower-risk design.

01

The situation

An internal team was receiving automation requests from across the business — by email and chat, with no consistent triage or audit trail. The goal: a single front door that turns each submission into a tracked, labelled work item on a GitHub board, so every request enters the same queue with the same status from the first second.

Input

A structured request form

One intake form — requester, business area, process, pain, expected value, priority — so every idea arrives in the same shape.

Output

A GitHub Issue on the board

A work item with a meaningful title, the request details in the body, and a status:intake label that drops it into the triage column automatically.

02

The turn

The first design wasn't the mistake. Testing the fast path is how you find the real boundary — fast.

The judgment isn't in avoiding the constraint; it's in what you do when you hit it. Here the tenant's security policy redrew the architecture — and the redesign was the stronger system, because it was forced toward the place the work was already allowed to run. What follows is the decision as it actually unfolded, not a tidied-up version.

How it unfolded

Four moves — from the efficient hypothesis, through the guardrail, to the design that shipped. Tap any to expand.

What I did
  • Built the shortest credible path — Forms trigger, get response details, compose the payload, POST it to the GitHub API.
  • Minimal moving parts, no extra tooling, shippable in an afternoon. The textbook first move.
  • Stood it up and tested it as a working hypothesis, not as the final answer.

Why start hereTesting the fast path is the cheapest way to find the real boundary. It surfaced the constraint in one save — faster than designing around a wall before confirming the wall exists.
What happened
  • On save, the Data Loss Prevention policy classified the generic HTTP connector as blocked and suspended the flow — so the call never reached GitHub.
  • A connector that can post data to any endpoint is restricted by default in most enterprise tenants. This is governance working as designed, not a bug.
  • Respecting the boundary, rather than quietly working around it, was the only acceptable starting point.

The deciding insightEvery cloud option failed on two axes at once: each needed a fresh security approval, and none could reach a self-hosted GitHub server behind the firewall. The internal host was never reachable from any cloud connector — so the constraint was never only DLP. Moving execution inside the network resolved both with one decision, and asked security for nothing it hadn't already approved.
The shape
  • Power Automate keeps doing only what it's allowed to — watch the form and send an email, both business-group connectors that DLP permits.
  • That email is the signal. A UiPath robot, running inside the network, picks it up and creates the GitHub Issue from there — reachable because the call now originates on-prem.

Email payload

JSON, not free text

  • A nicely formatted email body forces the robot to scrape with regex — it breaks on the first layout change.
  • Power Automate emits the same GitHub JSON in the body (or a .json attachment); UiPath just deserializes. Format-proof.
Process shape

A queue, not a monolith

  • One process that reads mail and posts in a single shot loses retry and visibility, and vanishes without a trace when it fails.
  • Dispatcher enqueues; Performer consumes and POSTs — automatic retry, an exception lane, and a full run history for audit.
Idempotency

No duplicate Issues

  • A restart or a duplicated poll re-reads the same email and opens a second Issue — quietly polluting the repo.
  • Handled mail is moved to a processed folder, or deduplicated on the Forms response ID. Reprocessing becomes a no-op.
Secrets

Token in the vault

  • A PAT hardcoded in the workflow leaks into source and can't be rotated cleanly.
  • It lives as an Orchestrator Credential asset, fetched at runtime — auditable, and rotatable without touching the build.
Trigger & runtime — the feasibility gate

Event vs poll, and the capacity that decides it

  • Trigger: an Integration Service email trigger if the estate has it; otherwise a scheduled dispatcher polling the mailbox. Latency of a few minutes is irrelevant for intake.
  • The real gate is unattended robot capacity. Without an available unattended runtime, none of this runs — so it's the first thing to confirm, before any of the above.
05

Why the constraint made it stronger

These gains aren't a lucky side effect of the workaround. Each follows directly from moving execution into the network and putting it under orchestration — they are the design, not an accident of it.

01 · Reachability

Solved, not just unblocked

The internal GitHub server was never reachable from the cloud. An on-prem robot talks to it natively — closing a second problem the first design would have hit even with DLP open.

02 · Audit

Governance-grade trail

A queue gives automatic retry, an exception lane, and full run history. A fire-and-forget HTTP call leaves nothing behind when it fails. For an internal intake process, that trail is a requirement.

03 · Security

Zero new footprint

The whole pipeline runs on tools already approved for the tenant. No connector exception, no firewall change, no ticket to security — which is also why it shipped instead of waiting on a review board.

04 · Cost

No new spend

It reuses the existing UiPath estate rather than adding external SaaS or premium licensing. The constraint pushed the solution toward infrastructure the company already pays for.

07
The principle underneath

  

    0 new security exceptions
    100% sanctioned tooling
    Full audit trail · queue history
    1 front door for every request
  

  

    
Reading an organisation's constraints early — and designing inside its sanctioned tooling — is cheaper and more durable than seeking exceptions to it. The fast first design isn't waste; it's how you find the real boundary quickly. The work is in what happens next.

    
The boundary didn't compromise the system — it pushed it toward a better shape: reachable, auditable, low-risk, and built from tools the company already runs. That's the difference between a workaround and a design.
